# Claude Code Adapter: Enable or Disable Rules

This adapter applies only to the hook scripts in the myhooks plugin's `hooks/` directory (called `<hooks>` below).

Each script has a `RULE_ENABLED` map:

```python
RULE_ENABLED = {
    "git-checkout": True,
    "git-add-all": True,
}
```

Toggle one rule by changing its value between `True` and `False`. Do not edit `settings.json`. This operation does not add, remove, or disable a registered hook script, and it does not require a reinstall.

## Rule identifiers

Bash rules in `pretooluse_bash.py`:

- `git-checkout`: blocks git checkout.
- `git-reset`: blocks git reset in any form, including `git -C <path>`.
- `git-add-all`: blocks widespread git add (`-A`, `-a`, `--all`, `.`).
- `git-no-verify`: blocks `--no-verify` on commit or push. Disabled by default.
- `git-destructive`: blocks git clean, push --force, and rebase.
- `git-stash`: blocks git stash.
- `rm-command`: blocks rm. Deletions need explicit user approval.
- `sed-command`: blocks `sed -i`. Use the Edit tool instead.
- `npm-no-save`: blocks npm installs that lack `--save` or `--save-dev`.
- `make-no-makefile`: requires absolute `-f` or `-C` paths for make, and rejects relative paths.

File-edit rules in `pretooluse_file.py`:

- `autogen-files`: blocks edits to files under generated or autogenerated directories.
- `write-existing-file`: blocks the Write tool on an existing file, because Write replaces the whole file. Use Read and then Edit.
- `go-error-suppression`: blocks discarding a Go function's last return value with a blank identifier.
- `go-nilnil-return`: blocks `return nil, nil` in non-test Go files.
- `go-nolint-ban`: blocks any nolint directive in added Go content.

Post-edit rules in `posttooluse_file.py`:

- `python-syntax`: runs a syntax check on Python files after an edit.
- `python-local-imports`: flags imports inside functions or classes, unless the line carries the nolint directive for avoiding an import cycle.

## Workflow

1. Identify the rule. Search the three scripts for the identifier or a keyword.
2. If several rules match, use AskUserQuestion to confirm the exact identifiers. Bulk changes such as "disable all git rules" need confirmation by name before anything changes.
3. Change only the confirmed values in `RULE_ENABLED`.
4. Re-read the changed map and report the final state, with the behavior each enabled rule now permits or blocks.

Examples:

- "Disable the git checkout block": set `"git-checkout": False`, then confirm that git checkout is now allowed.
- "Re-enable the rm block": set `"rm-command": True`, then confirm that rm is blocked again.
- "Disable all git rules": confirm the five git identifiers (`git-checkout`, `git-reset`, `git-add-all`, `git-destructive`, `git-stash`), then set each to `False`.

Treat "hook" in this workflow as one rule, not a whole script.
